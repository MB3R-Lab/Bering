# Declared eBPF OTLP sources

Bering accepts OpenTelemetry traces produced by an explicitly declared eBPF
collector. Applications do not need an OpenTelemetry SDK when their collector
observes supported Linux processes and exports OTLP from outside those processes.
The original `ebpf-obi` declaration remains supported unchanged; `ebpf-otlp`
adds a required, validated collector name for other OTLP-producing collectors.

Bering does not run OBI. The Bering binary and Helm pod remain unprivileged.
OBI is a separate Linux deployment and needs the kernel access and privileges
documented by the OBI project.

## Runtime ingest

Declare each OBI collection boundary under `sources` in the serve config:

```yaml
server:
  listen_address: ":4318"
sources:
  - id: obi-main
    type: ebpf-obi
    domain: production
    capture_directory: /var/lib/bering/obi-capture
```

For another OTLP-producing eBPF collector, use a product-neutral declaration:

```yaml
sources:
  - id: collector-main
    type: ebpf-otlp
    collector: collector-name
    domain: production
    capture_directory: /var/lib/bering/collector-capture
```

This registers:

```text
POST /sources/obi-main/v1/traces
```

Configure an OTLP/HTTP exporter with either the source base URL, when the
exporter appends `/v1/traces`, or the complete traces URL. For example, OBI's
common endpoint can be:

```text
http://bering:4318/sources/obi-main
```

The standard `POST /v1/traces` endpoint remains the generic OTLP source. It is
not relabelled as eBPF. Source-scoped eBPF ingest is currently HTTP only; the
standard OTLP/gRPC listener does not select a declared eBPF source.

Source fields have the following meaning:

- `id` is the URL-safe source identifier and must be unique in one Bering
  process.
- `type` is `ebpf-obi` for the backward-compatible OBI declaration or
  `ebpf-otlp` for a named collector.
- `collector` is required for `ebpf-otlp`, is normalized to lowercase, and
  must match `[a-z0-9][a-z0-9._-]{0,63}`. `ebpf-obi` continues to imply `obi`.
- `domain` identifies one collection deployment. Use the same domain for OBI
  agents whose trace IDs share a namespace. Do not use a hostname or collector
  replica ID. An omitted domain becomes `default`.
- `capture_directory` is optional. When set, Bering writes the accepted wire
  payload before discovery. The directory must be writable by Bering.

The Helm chart exposes the same list as `config.sources`. A capture path below
`/var/lib/bering` needs chart persistence or another writable volume. Enabling
an eBPF source does not change the chart's non-root, read-only, capability-free
security context and does not deploy OBI.

## Batch input and replay

Use `ebpf-obi` to distinguish retained OBI exports from ordinary trace files:

```bash
bering discover \
  --input /var/lib/bering/obi-capture \
  --input-type ebpf-obi \
  --source-domain production \
  --out bering-model.json \
  --snapshot-out bering-snapshot.json
```

For a named collector, use the same decoder with an explicit declaration:

```bash
bering discover \
  --input /var/lib/bering/collector-capture \
  --input-type ebpf-otlp \
  --collector collector-name \
  --source-domain production \
  --out bering-model.json \
  --snapshot-out bering-snapshot.json
```

The connector accepts OTLP JSON, newline-delimited OTLP JSON export requests,
binary OTLP protobuf, and gzip-compressed JSON or protobuf captures. Directory
inputs are read in lexical path order. Malformed or truncated records fail the
load; Bering does not repair IDs or conflicting attributes.

Runtime capture retains the actual HTTP request body and its wire encoding.
Capture failure rejects the ingest request instead of silently producing a
model without replay evidence. Treat captures as telemetry: they can contain
attributes supplied by applications or infrastructure and need the same access
controls and retention policy as other trace storage.

## Identity, domains, and provenance

The connector preserves OTLP trace, span and parent IDs, span kind, operation,
resource identity, instrumentation scope, network peer attributes and process
attributes when the collector actually exported them. Declaring a source does not invent
missing values and is not proof that a span was generated by eBPF.

Snapshots report source type `ebpf`, the declared collector, the capture or
runtime source reference, and the collection domain in observation evidence.
The source boundary prevents identical trace/span IDs from different collectors
or collection deployments being joined. Legacy OBI domains retain their
`ebpf:<domain>` namespace; named collectors use the disjoint
`ebpf-otlp:<collector>:<domain>` namespace. Bering does not rewrite the OTLP
trace, span, or parent IDs to achieve this isolation.

Runtime eBPF admission uses receiver time to assign a batch to the active
window. Original event timestamps remain descriptive evidence; disagreement
between agent and receiver clocks does not discard an otherwise valid export.
Configured memory limits and their dropped-observation counters still apply.

`service.name` is required to create a named service. `service.instance.id`,
host, container and process attributes improve instance evidence when present,
but OBI does not guarantee all of them for every protocol or runtime. In
particular, process PID and executable name are not required connector fields.

## Structural dependencies versus execution context

Bering distinguishes two kinds of evidence:

- An exact, unambiguous trace ID plus parent span ID produces an
  `execution_link`. This is causal caller-to-receiver evidence.
- A client span with an observed HTTP/RPC operation and a consistent reported
  peer can produce a `client_dependency` when no exact receiver exists. This is
  a structural dependency only. Its evidence records that server receipt and
  execution context were not observed.

Address, port or timing alone never creates trace ancestry. If an exact
receiver exists, Bering does not replace it with a peer-derived dependency.
Conflicting IDs or peer attributes remain warnings/unknowns rather than being
resolved arbitrarily.

Inbound endpoints require an observed server span. HTTP method/route and
gRPC service/method attributes identify their respective endpoints; an outgoing
client request without a parent does not become an inbound operation. A
client-only dependency may terminate at a scoped logical network endpoint
whose service name and physical instance remain unknown.

## Replica and placement limits

Trace observations do not establish desired replica counts, scheduler
placements, availability zones or shared-fate groups. A discovered service has
the model's compatibility placeholder replica value, with configured count
unknown, unless an explicit overlay or
topology input supplies the configured count. Peer placeholders likewise carry
unknown physical identity and configured-replica warnings. Do not interpret
the number of observed processes or `service.instance.id` values as deployment
inventory.

## Unsupported inputs and behavior

- Raw kernel events, packet captures and network-flow records are not accepted;
  the source consumes OTLP trace exports produced by OBI.
- Bering does not install, configure, supervise or grant privileges to OBI.
- The connector does not infer causal links from topic names, timestamps,
  addresses or ports.
- Missing server receipts, process metadata, instance identity and configured
  replica counts remain explicit partial or unknown evidence.
- Source declaration does not turn generic SDK spans sent to the source URL
  into verified eBPF observations; provenance states the configured boundary.
